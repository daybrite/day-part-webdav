Request policy, cancellation and constrained networks

Admission is checked before each attempt. Applications report Available, Offline, Constrained or Expensive; defaults defer constrained/expensive requests. The request also forwards the corresponding native HTTP policy flags. These are not a universal OS network monitor: applications must supply portable state, and platform enforcement varies. Changing admission state does not undo a transfer already in progress; dropping its future cancels it.

Only safe reads retry transient DNS/connect/I/O/timeouts and 408, 423, 425, 429, 500, 502, 503, 504. Authentication failures, preconditions, quota failures, XML errors, TLS errors and size violations return directly. Retry-After is a lower bound; delays beyond 15 seconds return to the caller instead of sleeping indefinitely. HTTP-date parsing uses the local wall clock on native platforms and an exposed server Date header on web; if web lacks that date, an HTTP-date delay is conservatively deferred. No API promises precise radio usage or background execution.

Mutations have one application-level attempt even when HTTP defines their method as idempotent. Native stacks may perform their own connection/authentication handling. A lost response is MayHaveApplied; neither cancel nor timeout means rollback. A persistence outbox must retain that intent and verify remote bytes before retrying publication. No credentials or telemetry are logged by this crate.

Protocol and parser decisions

RFC 4918 defines DAV methods and Multi-Status; RFC 9110 defines validators, HTTP conditionals and ranges. A 207 is a container of outcomes, not universal success. Missing optional properties can legitimately have 404 statuses. Listings expose those statuses rather than deleting resources or inventing empty values.

Href resolution is same-origin and inside the configured root. Dot segments, encoded separators, malformed escapes and duplicate normalized hrefs fail closed. Decoded input segments are encoded once; a literal plus is never form-decoded to a space. Nextcloud's escaped plus and a client's literal plus resolve to the same resource. XML rejects DTDs and invalid UTF-8, bounds bytes/nodes/depth/resources, and retains unknown properties. Original XML fragments can reference namespace declarations on ancestors; they are diagnostic fragments, not standalone XML documents.

A range read needs a strong validator. A 206 must match Content-Range, body size, ETag and identity representation. A 200 is Restart and may replace a prior download, never extend it. This stricter-than-minimum interoperability profile intentionally rejects responses with insufficient validation evidence. Weak ETags remain valid for If-None-Match caching but cannot safely drive replacement or resume.

What Nextcloud compatibility requires

Use an authenticated private Files DAV collection under /remote.php/dav/files/USER/, normally with an app password for accounts using external login or 2FA. The server/reverse proxy must allow DAV verbs and headers and preserve validators. Public shares use a different endpoint and may require extra request headers; this initial client does not implement that profile. Nextcloud Files DAV documentation.

Configure usable per-user quota, proxy request/body/time limits and a collection where the account can create, read and delete its own test resources. Browser access additionally requires deliberate CORS configuration; a desktop client working does not imply a browser will work. Nextcloud chunk upload, locking extensions and RFC 6578 change reports are not prerequisites for this foundation and are not automatically enabled. End-to-end sync onboarding must probe the actual user's path and permissions.
